## 1. Root Cause Summary (`DF-022` & `DF-024`)

### 1.1 Control-Plane Split-Brain & Non-Transactional Financial Mutations (`DF-022`)
Previously, Union Bank integration services and generic payment/reconciliation modules imported `query` / `pool` from `config/db.js` instead of resolving each dairy's isolated PostgreSQL tenant database via `tenantDbManager.getStrictTenantDb(organizationId, { bypassCache: true, strictOperational: true })`:
- `UnionBankReconciliationService.ts`, `UnionBankSubmissionService.ts`, `UnionBankStatusInquiryService.ts`, `payout.service.ts`, `reconciliation.service.ts`, `batch.service.ts`, `payment.controller.ts` (`getFarmerPaymentOverview`), `receipt.service.ts`, `settlement-calculation.service.ts`, and `BankFileService.ts` routed operational reads/writes to the central control-plane pool (`config/db.js`).
- `reconciliation.service.ts` contained `resolveDefaultOrgId()`, which fell back to `SELECT id FROM organizations LIMIT 1` or a fabricated `crypto.randomUUID()` when webhook payloads lacked an `organizationId`.
- External bank API calls (`UnionBankSubmissionService.submitBatch`, `UnionBankStatusInquiryService.queryItemStatus`) and batch item settlements ran either before opening transactions or using non-transactional global queries.
- `fail_customer_payout` and `reverse_customer_payout` needed additive replay/conflict protections, and `payment_batch_items` lacked `'REVERSED'` in `chk_batch_item_status`.

### 1.2 Zero Debit Account Fallback & Unmasked Credentials (`DF-024`)
- `UnionBankSubmissionService.ts`, `UnionBankApiClient.ts`, `UnionBankFileSerializer.ts`, `StandardNeftSerializer.ts`, and `apps/dfarm-dairy-admin/src/pages/payments/PaymentRegister.tsx` fell back to `'00000000000000'` / `'000000000000'` and/or global `process.env['UNION_BANK_DEBIT_ACCOUNT']` across tenants.
- `UnionBankValidator.validateAccountNumber()` accepted all-zero strings and echoed unmasked inputs in error strings.
